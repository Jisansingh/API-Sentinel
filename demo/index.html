API Sentinel

Sample traffic sends requests to the deliberately vulnerable demo shop (needs the backend started with the demo target on). “Run scan” analyses everything captured and stores deduplicated alerts. These apply across every section below.

Shadow APIs

Routes seen in traffic but absent from the OpenAPI specification. Routes that only ever answered 404/405 and Sentinel’s own routes are excluded. Without a loaded specification nothing can be confirmed as shadow.

Request activity and behavioral metrics available from the current API responses.

Request volume is shown per endpoint because the API does not expose a timestamped traffic series (only per-endpoint aggregates and each endpoint’s last-seen time), so a true over-time trend line cannot be built without a backend change.

Live findings

Not stored. Recalculated on every refresh over short rolling windows ending now (bursts: last minute; ID enumeration: last 5 minutes; token replay: last hour), so a finding disappears once its traffic ages out. Use Run scan to keep one as an alert.

Behavioral baselines

Per-endpoint and per-caller behavior over the backend’s baseline window (shown above) of captured traffic: request rate, payload size and server-error rate, with the current hour compared to the same weekday/hour in earlier weeks.

Real traffic history & adaptive baselines

Hourly history of the real requests this Sentinel instance captured (never the synthetic benchmark), kept across restarts. A baseline is trusted only after traffic on at least 3 days, 48 hours apart and in 6 active hours, so a single burst never counts as normal. Hours that overlap an alert or exceeded the trusted baseline are quarantined and never learned; until new evidence qualifies, the last trusted baseline is kept. Run scan stores newly trusted baselines.

Stored abuse alerts with severity, detection reason, timestamps and request evidence.

What is detected and what the risk score means
Scraping
One client IP sends more than 10 requests in 60 s across at least 5 different paths, or more than 20 different paths in 60 s, or more than 100 requests across at least 20 paths in an hour (“low and slow”).
BOLA enumeration (attempt)
One actor tries more than 10 different object IDs on the same route within 5 minutes, or paced over up to an hour (“low and slow”), and at least half are refused (401/403/404). It shows probing, not that anything was read.
BOLA (confirmed)
A successful (2xx, with content) read of an object owned by another user. Needs ownership context: an ownership file, or the synthetic demo users when the demo shop is enabled.
BOLA attempt (blocked / inconclusive)
A request for another user’s object that was refused (401/403/404), or whose response (204, 3xx, 5xx, other 4xx) does not show whether data was disclosed. Recorded as an attempt, never as a confirmed vulnerability.
Repeated access denials
One caller receives at least 10 refusals (401/403) within 5 minutes, at least half of its requests. Refusals already explained by an enumeration alert are not counted twice.
Anomalies (rate, server errors, payload size)
The current hour exceeds the same weekday/hour in at least 3 earlier weeks (so a recurring peak is normal); a 5xx spike or oversized request bodies compared with the previous 7 days (at least 20 requests). Without that history these rules stay silent.
Token replay
One credential (stored as a keyed fingerprint, never the token) used from at least 4 IPs within an hour, each switch to a new IP coming within 60 s of the credential’s previous request.
Shadow API
A route that answered in traffic but is not in the loaded OpenAPI specification.

Risk score (0–100), computed by the backend: base weight of the detection (BOLA 35, scraping 30, token replay 35, access denials 25, anomalies 20, BOLA attempts 15) + up to 30 for magnitude (+10/+20/+30 at 3×/6×/12× the threshold) + 10 for a write method + 10 for a sensitive path segment (admin, internal, export, debug), capped at 100. Bands: High ≥ 70 Medium 40–69 Low < 40. Each alert’s “Score breakdown” shows the exact parts.

Rules and thresholds were tuned on synthetic traffic; they are signals for an analyst, not proof of an attack.

Alert investigation

Persistent alerts

Stored in the database and deduplicated by detection type, actor and endpoint. Only Run scan creates or updates them; they survive restarts and keep the status and note you set.

Risk & Analytics

An explainable risk score for every observed endpoint, plus the distribution of stored alerts. Scores are computed by the backend on a 0–100 scale (High ≥ 70, Medium 40–69, Low < 40); times are UTC.

Endpoint risk scores

Computed by the backend for every observed endpoint, 0–100: exposure (max 20), authentication (20), data sensitivity (20), behavior anomalies (15) and security events (25). Each factor lists its evidence; inputs Sentinel cannot see are named and add nothing. Only open/acknowledged alerts count, once per detection type. Score history is recorded by Run scan and alert triage.

Alert-based ranking

Gateway and per-endpoint rate-limit enforcement: what was allowed, flagged, blocked or rate-limited, and why.

Access control

Per-endpoint rate limits and the gateway firewall. Events are stored per time window and counted, never with tokens, request bodies or query values. Identity is decided by the server: a registered credential fingerprint, the admin key, or otherwise the client address. Headers that merely claim a role are ignored and listed here.

Registered principals, the VP quota multiplier, and the rate limit configured for every endpoint.
